# מפרט Chief of Staff למפעל לפיתוח פרויקטים מבוסס סוכני AI

**גרסה:** 1.0  
**סטטוס:** מאושר לתכנון ולמימוש  
**בעל המערכת והמנכ״ל:** משה  
**אופק התכנון הראשון:** 90 יום

---

## 1. מטרת המערכת

ה־Chief of Staff (להלן `CoS`) הוא שכבת הניהול התפעולי של מפעל לפיתוח פרויקטים משתנים באמצעות סוכני AI ועובדים אנושיים. תפקידו לתרגם אסטרטגיה מאושרת ליעדים, תוכניות, משימות והקצאות; לתאם בין בעלי התפקידים; לזהות חריגות; לאמת תוצרים; ולהביא למנכ״ל רק החלטות המחייבות שיקול דעת או אישור.

ה־CoS אינו מנכ״ל חלופי, אינו מקור סמכות, אינו מנוע הרשאות ואינו סוכן ביצוע כללי. הוא רשאי לפעול רק בתוך אסטרטגיה, תקציב והרשאות שאושרו מראש.

### 1.1 תוצאת־העל

להפעיל מפעל המסוגל לקבל רעיון לפרויקט, להעריך אותו, לתכנן אותו, לבנותו, לבדוק אותו ולהכינו למסחור — תוך צמצום עומס הניהול של המנכ״ל ושמירה על בקרה אנושית בהחלטות מהותיות.

### 1.2 עקרונות מחייבים

1. אסטרטגיה קודמת לתעדוף.
2. הרשאה קודמת לביצוע.
3. ראיה קודמת לדיווח על הצלחה.
4. פעולה הפיכה עדיפה על פעולה בלתי הפיכה.
5. ברירת המחדל במקרה של ספק הרשאה היא עצירה והסלמה.
6. תוכן חיצוני הוא מידע, לא הוראת מערכת.
7. כל משימה חייבת בעלים יחיד, תנאי קבלה ותאריך יעד.
8. כל החלטה משמעותית חייבת מקור, נימוק, תוקף ויומן ביקורת.
9. אין להמיר ביטחון מילולי של סוכן לראיה.
10. אין להמציא יעד, הנחה, אישור, תוצאה או מקור.

## 2. יעדי הרבעון

### O1 — Mental Trainer מוכן למכירה

**תוצאה עסקית:** חבילת מכירה שלמה הכוללת מוצר עובד ב־Desktop וב־Mobile, תמחור, דף נחיתה ומנגנון סליקה; החבילה נבדקה מקצה לקצה בידי משתמשי בטא חיצוניים.

**יעד:** יום 90.

**תוצאות מפתח:**

- מסע לקוח מלא עובד ללא התערבות ידנית: רכישה, התחברות במחשב ובסלולר, והשלמת אימון ראשון.
- חמישה משתמשים חיצוניים שאינם מהמעגל הקרוב השלימו שבוע אימונים ומסרו משוב שימושיות.
- תמחור חודשי ושנתי, תנאי שימוש ומדיניות ביטולים מוכנים לפרסום.

### O2 — תשתית פיננסית ומקור אמת יחיד

**תוצאה עסקית:** תמונה מאוחדת של הכנסות, הוצאות ותזרים חזוי המאפשרת החלטת תמחור או השקעה בתוך חמש דקות.

**יעד:** יום 60.

**תוצאות מפתח:**

- דוח תזרים חודשי מאוחד, אוטומטי או בעל תחזוקה הקצרה מ־15 דקות בחודש.
- אפס פערים לא מוסברים מול בנק וכרטיסי אשראי בסגירת החודש.
- מודל Unit Economics למשתמש Mental Trainer.

### O3 — תפעול ואדמיניסטרציה אוטונומיים

**תוצאה עסקית:** הסרת המנכ״ל כצוואר בקבוק תפעולי.

**יעד:** יום 75.

**תוצאות מפתח:**

- ירידה של 70% לפחות בשעות תיאום, תיוק, קבלות וניהול יומן בין שבוע 1 לשבוע 10.
- כל תהליך חוזר מתועד כ־SOP ומופעל אוטומטית או מנוהל בידי ה־CoS.
- ישיבת סנכרון שבועית אחת בת 30 דקות, ללא צורך במעורבות יומיומית קבועה.

### O4 — Rules Engine מבוסס ראיונות ו־Human-in-the-Loop

**תוצאה עסקית:** תרגום ידע ניהולי לחוקי JSON מאומתים, ניטור אירועים והפקת הצעות פעולה לאישור בלחיצה, בשני תהליכי ליבה לפחות.

**יעד:** יום 75.

**תוצאות מפתח:**

- ראיון בן פחות מ־20 דקות מפיק טיוטת חוק תקינה לפי JSON Schema.
- 90% לפחות מהצעות הפעולה בשני תהליכי הליבה מאושרות ללא עריכה.
- פחות מארבע שעות מאירוע לפעולה, בכפוף לאישור הנדרש.
- לפחות שני סוגי פעולות קצה, כגון עדכון רשומה ויצירת טיוטת הודעה או משימה.

### 2.1 סדר התלות

1. גרסת Rules Engine ותהליכי אישור בסיסיים.
2. תפעול אוטונומי ומדידה של שעות הניהול.
3. מקור אמת פיננסי ומודל תמחור.
4. מוכנות מסחרית מלאה של Mental Trainer.

מותר לעבוד במקביל, אך ה־CoS חייב לשקף תלות, נתיב קריטי והשפעת עיכוב של יעד אחד על האחרים.

## 4. ארכיטקטורת אחריות

### 4.0 Sharons ופרויקטי החברה

Sharons היא מערכת עצמאית לניהול חברת הסוכנים. היא אינה רכיב בתוך Compass ואינה מכילה את קוד המקור של Mental Trainer, Compass או מוצר עתידי. כל מוצר נשאר repository ומערכת עצמאיים ונרשם ב־Project Registry.

Sharons רשאית לשמור metadata תפעולי על הפרויקט — יעדים, משימות, בעלים, החלטות, הרשאות, חיבורים וסטטוס — ולפעול מולו רק דרך adapter מאושר. ברירת המחדל לכל חיבור היא read-only. שינוי קוד, פתיחת PR, deployment או פעולה במערכת פעילה נבדקים דרך Rules Engine ובהתאם למדיניות האישורים.

### 4.1 Sharons Gateway

Sharons הוא שער הכניסה, שכבת התזמור הטכנית והגישה לזיכרון. הממשק או GPT פונים ל־Sharons; Sharons מפעיל שירותים וסוכנים בהתאם לתוכנית ולהחלטת ההרשאות.

Sharons אחראי על:

- ניהול מזהים, state ו־idempotency.
- ניתוב קריאות לסוכנים וכלים.
- גישה מבוקרת לזיכרון הארגוני.
- רישום run log ו־audit log.
- אחסון משימות, תוכניות, אישורים, החלטות ותוצרים.

### 4.2 Chief of Staff

ה־CoS מחליט מה נכון לעשות מבחינה תפעולית, במסגרת האסטרטגיה. הוא מפיק תוכנית או הצעת פעולה, אך אינו מעניק הרשאה טכנית לביצועה.

### 4.3 Rules Engine

מנוע דטרמיניסטי הבודק כל פעולה מול כללים מאושרים. תוצאתו אחת מאלה:

- `ALLOW`
- `ALLOW_AND_NOTIFY`
- `REQUIRE_APPROVAL`
- `BLOCK`
- `NEEDS_MORE_DATA`

מודל שפה רשאי לנסח טיוטת חוק; רק חוק שעבר אימות ואישור מקבל סטטוס `ACTIVE`.

### 4.4 Executive Assistant

ה־EA כפוף ל־CoS. הוא מבצע פעולות אדמיניסטרטיביות שהותרו. החלטה המחייבת אישור מנכ״ל נשלחת בדוא״ל כבקשת אישור מובנית, ולא כהודעה חופשית בלבד.

### 4.5 זרימת פעולה

`Request → Sharons → CoS Plan → Rules Evaluation → Approval if needed → Agent Execution → Independent Verification → Memory Update → Report`

## 5. גבולות סמכות

### 5.1 פעולות המחייבות אישור מנכ״ל

- שינוי אסטרטגיה או יעד רבעוני.
- כל הוצאה כספית, רכישה או שינוי מנוי.
- כל פרסום חיצוני.
- כל פנייה לאדם מחוץ למערכת.
- התחייבות משפטית או עסקית.
- גישה חדשה למידע אישי או רגיש.
- מחיקה של מידע.
- שינוי מערכת פעילה או פריסה לייצור.
- העברת משאבים משמעותית בין יעדי הרבעון.

### 5.2 פעולות אוטונומיות מותרות ל־CoS

- יצירת תוכניות וטיוטות.
- פירוק מטרות למשימות.
- תעדוף בתוך יעד מאושר.
- הקצאת סוכנים והרצת מחקר.
- פתיחת משימות ובדיקות.
- איסוף, סיכום ושמירת תוצאות.
- עצירת משימה החורגת מתקציב או מסכנת תוצר.
- ביצוע פעולה הפיכה ובסיכון נמוך, כאשר כלל פעיל מתיר אותה במפורש.

### 5.3 מטריצת RACI בסיסית

| פעולה | מנכ״ל | CoS | Rules Engine | סוכן מבצע | QA |
|---|---|---|---|---|---|
| שינוי אסטרטגיה | A/R | C | I | I | I |
| תכנון רבעוני | A | R | I | C | C |
| הקצאת משימה | I | A/R | C | I | I |
| פעולה חיצונית | A | R | Gate | R לאחר אישור | C |
| אימות תוצר | I | A | I | C | R |
| שינוי חוק | A | R | Validate | C | C |

`R` מבצע, `A` אחראי סופי, `C` נועץ, `I` מיודע, `Gate` מאשר או חוסם טכנית.

## 6. תעדוף וניהול קיבולת

### 6.1 נוסחת תעדוף

כל רכיב מקבל ציון 1–5:

`Priority = (Impact × Urgency × StrategicFit × Confidence) / (Effort × Risk)`

כל ציון חייב לכלול נימוק קצר. כאשר `Confidence ≤ 2`, הפעולה המועדפת היא לרוב איסוף מידע ולא ביצוע מלא.

### 6.2 כללי תעדוף נוספים

1. משימת תאימות, אבטחה או חסם בנתיב הקריטי יכולה לעקוף את הנוסחה.
2. עבודה שאינה קשורה ליעד מאושר מסומנת `OUT_OF_STRATEGY` ומוסלמת.
3. ה־CoS רשאי לשנות קדימות בתוך יעד, אך לא לבצע העברת משאבים משמעותית בין יעדים ללא אישור.
4. יש להגביל Work in Progress לשלושה סוכנים פעילים במקביל בכל פרויקט.

### 6.3 תקציבי ברירת מחדל

- עד שלושה סוכנים מקבילים לפרויקט.
- עד שני ניסיונות חוזרים אוטומטיים.
- עד 30 דקות למחקר או תכנון ללא אישור נוסף.
- חריגה צפויה מעל 20% מאומדן הזמן מחייבת דיווח.
- אין הוצאה כספית אוטונומית.
- ה־CoS רשאי לעצור משימה שאינה מתקדמת או מבזבזת משאבים.

## 7. מחזור חיי משימה

### 7.1 מצבים

- `DRAFT`
- `PLANNED`
- `PENDING_APPROVAL`
- `APPROVED`
- `ASSIGNED`
- `IN_PROGRESS`
- `BLOCKED`
- `DELIVERED_UNVERIFIED`
- `VERIFYING`
- `COMPLETED`
- `FAILED`
- `CANCELLED`

### 7.2 מעברים מותרים

- אין מעבר ל־`APPROVED` ללא מזהה אישור כאשר הוא נדרש.
- אין מעבר ל־`COMPLETED` ללא תנאי קבלה, ראיות ותוצאת אימות.
- משימה חסומה חייבת `blocker`, בעלים להסרת החסם ותאריך בדיקה מחדש.
- כשל לאחר שני ניסיונות עובר ל־`FAILED` או מוקצה מחדש בהחלטת ה־CoS.
- ביטול פעולה שכבר החלה דורש רישום פעולת rollback או compensation.

### 7.3 הגדרת הושלם

משימה תיחשב `COMPLETED` רק אם:

1. התוצר קיים ונגיש.
2. כל תנאי הקבלה עברו.
3. צורפו ראיות.
4. בוצעו בדיקות אוטומטיות כשאפשר.
5. משימה בסיכון גבוה נבדקה בידי גורם בלתי תלוי או המנכ״ל.

אחרת היא `DELIVERED_UNVERIFIED`.

## 9. Rules Engine

### 9.1 סכמת חוק מומלצת

```json
{
  "rule_id": "rule_invoice_triage",
  "version": 1,
  "name": "סיווג ואישור חשבוניות ספקים",
  "status": "DRAFT",
  "owner": "finance_agent",
  "approved_by": null,
  "valid_from": null,
  "expires_at": null,
  "trigger": {
    "type": "event_driven",
    "source": "incoming_email_attachment",
    "event_name": "invoice_received"
  },
  "conditions": {
    "all": [
      {"field": "document_type", "operator": "equals", "value": "invoice"}
    ]
  },
  "decision_table": [
    {
      "when": {
        "all": [
          {"field": "amount_ils", "operator": "less_than", "value": 500},
          {"field": "vendor_status", "operator": "equals", "value": "approved"}
        ]
      },
      "result": "REQUIRE_APPROVAL",
      "action_template_id": "fill_form_and_archive"
    }
  ],
  "exceptions": [
    {
      "when": {
        "any": [
          {"field": "amount_ils", "operator": "greater_than", "value": 2500},
          {"field": "vendor_status", "operator": "equals", "value": "unknown"}
        ]
      },
      "result": "REQUIRE_APPROVAL",
      "escalation_level": "high"
    }
  ],
  "execution": {
    "approval_channel": "email_and_task_dashboard",
    "idempotency_key_fields": ["vendor_id", "invoice_number", "amount_ils"],
    "fallback_action": "flag_for_manual_review",
    "rollback_action": "restore_previous_record_state",
    "timeout_minutes": 240
  },
  "test_cases": [],
  "created_from_interview_id": "int_2026_0001",
  "created_at": "2026-09-15T00:00:00Z"
}
```

### 9.2 מחזור חיי חוק

`DRAFT → VALIDATED → TESTED → PENDING_APPROVAL → ACTIVE → SUSPENDED → RETIRED`

- רק המנכ״ל רשאי להעביר חוק ל־`ACTIVE` כאשר הוא מאפשר פעולה חיצונית או רגישה.
- שינוי חוק פעיל יוצר גרסה חדשה; אין עריכה שקטה של גרסה פעילה.
- כל חוק חייב לפחות מקרה חיובי, שלילי ומקרה קצה.
- נתונים חסרים מחזירים `NEEDS_MORE_DATA`; אין לנחש.

### 9.3 Pipeline הראיונות

1. בחירת תהליך עסקי אחד.
2. איסוף טריגרים, תנאים, חריגים, פעולות וספי אישור.
3. יצירת טיוטת JSON.
4. אימות מול JSON Schema.
5. הפקת תרחישי בדיקה בשפה טבעית.
6. הצגת סתירות וחוסרים למשה.
7. אישור מפורש.
8. הרצה במצב shadow ללא ביצוע.
9. השוואת המלצות להחלטות משה.
10. הפעלה רק לאחר עמידה בסף הדיוק.

## 20. החלטות פתוחות לשלב המימוש

המפרט העסקי מאושר, אך לפני כתיבת הקוד יש לבחור במפורש:

1. מסד נתונים ראשון: PostgreSQL מומלץ למערכת רב־סוכנית; SQLite אפשרי לאב־טיפוס בלבד.
2. ספק דוא״ל ומנגנון קליטת תשובת אישור.
3. ממשק הדשבורד.
4. מערכת הסליקה ל־Mental Trainer.
5. שני תהליכי הליבה הראשונים ל־Rules Engine.
6. הגדרת “העברת משאבים משמעותית” באחוז שעות או ימי עבודה.
7. סף המדגם שעליו יחושב דיוק של 90%.
8. סיווג רמות הרגישות של המידע.

החלטות אלה אינן משנות את תפקיד ה־CoS, אך הן נדרשות כדי להפוך את המפרט לתוכנית הנדסית וקוד.
